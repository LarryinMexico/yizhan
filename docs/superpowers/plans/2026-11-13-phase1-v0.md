# Yizhan Phase 1 (v0) Implementation Plan

Date: 2026-11-13
Spec: `docs/superpowers/specs/2026-11-12-webhook-delivery-platform-design.md`
Target: a publicly usable v0 by **2026-12-10**, in about 40–60 hours (10–15 hours per week).

Goal: one event travels through all six stations — accept, persist, enqueue, deliver, record, retry — on a deployed AWS instance.

## Technology choices

| Purpose | Choice |
|---|---|
| Environment and tooling | `uv`, `ruff`, `pytest` |
| API | FastAPI, Pydantic, pydantic-settings |
| Database | PostgreSQL, SQLAlchemy 2 (async) + asyncpg, Alembic |
| Queue | Kafka (official `apache/kafka` image, single broker, KRaft), `aiokafka` |
| HTTP delivery | `httpx` |
| Cache and rate limiting | Redis, `redis-py` |
| Pages | Jinja2, server-rendered |
| Tests | Testcontainers (real PostgreSQL, Kafka, Redis) |
| Deployment | Docker Compose, Caddy (automatic HTTPS), GitHub Actions |

## Milestones

Every milestone follows the same loop: a one-page learning brief, the owner decides and writes the ADR, models implement everything except the hand-written parts, the owner reviews, and the verification commands are run.

### M0 Skeleton (Nov 13–16, about 6 hours)
- `uv init`, ruff and pytest configuration, a `/healthz` endpoint.
- `compose.yaml` starts PostgreSQL, Kafka, Redis, and the API.
- Public GitHub repository and CI (lint and tests).
- Learn: Docker images and containers, Compose, CI.
- Verify: after `docker compose up`, `curl localhost:8000/healthz` returns 200; CI is green.

### M1 API and database (Nov 17–23, about 12 hours)
- Tables and Alembic migration.
- API-key authentication (keys stored hashed).
- CRUD for applications and endpoints.
- `POST /v1/messages`: idempotency key, fan-out to one delivery per subscribed endpoint (no Kafka yet).
- Learn: SQL, transactions, unique constraints, FastAPI dependency injection.
- ADR-001 data model; ADR-002 why Kafka instead of PostgreSQL as the queue.
- Verify: the same idempotency key sent twice yields one message row; integration tests pass.

### M2 Kafka and the delivery worker (Nov 24–30, about 14 hours)
- The API publishes one Kafka record per delivery after the database write (key = endpoint ID).
- Models write `signing.py` (HMAC-SHA256), `ssrf.py` (blocks private addresses), and failing tests for the worker.
- **The owner hand-writes `worker.py`**: consume, sign, POST, record the attempt, update state, commit the offset — until the tests pass.
- Learn: topics, partitions, consumer groups, offsets, at-least-once delivery.
- ADR-003 when to commit the offset.
- Verify: an event reaches the mock receiver; killing the worker mid-delivery and restarting it still delivers the event, with no duplicate rows in `attempts`.

### M3 Retries, rate limiting, and the page (Dec 1–6, about 12 hours)
- **The owner hand-writes `backoff.py`** (exponential backoff with jitter).
- Retry scheduler (`FOR UPDATE SKIP LOCKED`); after 8 failures mark `failed` and publish to `deliveries.dlq`.
- Manual replay endpoint, Redis rate limiting, a minimal delivery-log page.
- ADR-004 retry timing in the database versus tiered retry topics.
- Verify: with the mock receiver returning 500, attempt count and spacing match the schedule (shortened in tests) and the final state is `failed`; a manual replay then succeeds.

### M4 Deployment (Dec 7–10, about 10 hours)
- Dockerfile, `compose.prod.yaml`, Caddy HTTPS.
- AWS: one 4 GB EC2 instance, security group open on 80/443/22 only, a budget alert. Confirm instance type and price on the official page before launch.
- Domain, GitHub Actions deployment, README and API documentation.
- Verify: an event sent to the public URL arrives at webhook.site with a signature; services recover after a reboot.

## Scope control

Not in phase 1: transactional outbox, Kubernetes, monitoring, the showcase app, the React dashboard. New ideas go to the phase 2 list.

If behind schedule, cut in this order: rate limiting, manual replay, the log page (use the API instead). Deployment is never cut.

## Definition of done

1. `uv run pytest` passes against real PostgreSQL, Kafka, and Redis.
2. After `docker compose up`, the `curl` commands in the README register an application, create an endpoint, send an event, and read its history.
3. A failing endpoint is retried on schedule and ends in `failed` after 8 attempts.
4. Killing the worker loses no event and creates no duplicate attempt row.
5. The public URL works, CI is green, and the owner has written four ADRs.
